# 데일리 업데이트 기준 V01

## 1. 문서 역할

이 문서는 운영 데이터를 특정 기준일까지 일관되게 갱신하고, 그 결과를
`MarketDataRepositoryV2`와 이후 분석·보고 단계에 전달하기 위한 현재 공통
기준이다. 데일리 업데이트의 최종 목표는 시스템 시각이나 실행 당일을
기준으로 삼는 것이 아니라, 사용자가 지정한 하나의 `target_as_of`를 모든
원천 데이터와 파생 결과에 끝까지 전달하는 것이다.

이 문서는 실행 계획 메모가 아니다. 아래에서 **공통 계약**과 **1단계의
상세 기준**을 권위 있게 정의한다. 2단계와 3단계는 각각 별도 상세 계약에서
정의하며, 4단계는 [분석·리포트·웹 반영 기준 V01](daily_update_phase4_analysis_reporting_web_contract_v01.md)에서
상세 계약을 정의한다. 5단계는 전체 흐름과 상속 규칙만 설명하는 상위
개요다. 개별 실행 결과와 검증 일지는 이 문서의 범위에 포함하지 않는다.

## 2. 전체 목표와 단계

### 2.1 전체 흐름

```text
target_as_of 입력
  → 원천 데이터 갱신
  → Repository V2 일관성 확보
  → 주봉·월봉 등 파생 데이터
  → 수급·펀더멘털·RS 등 분석 입력
  → 스캐너·전략·종목 리포트
  → 각종 랭킹·공포지수·웹 데이터
  → 검증
  → 배포
```

모든 단계의 기준일은 처음 입력한 `target_as_of` 하나다. 단계별로 오늘 날짜,
마지막 파일 날짜, 웹 화면의 최신 날짜를 따로 정하지 않는다.

### 2.2 단계별 범위

| 단계 | 이름 | 이 문서에서의 범위 |
|---|---|---|
| 1단계 | 데일리 업데이트 기반 | 원천 시장데이터와 Repository V2의 기준일 일관성. 상세 정의 |
| 2단계 | 주봉·월봉 파생 | 인증된 일봉에서 주봉·월봉을 파생하고 기간 완료 상태를 판정하는 기준 ([상세 계약](daily_update_phase2_weekly_monthly_derivation_contract_v01.md) 참고) |
| 3단계 | 분석 입력 갱신 | 수급·펀더멘털·시장·업종 RS 등 분석 입력의 기준일·권위·상태를 조율하는 기준 ([상세 계약](daily_update_phase3_analysis_inputs_contract_v01.md) 참고) |
| 4단계 | 분석·리포트·웹 반영 | 스캐너·전략·종목 리포트·랭킹·공포지수·`web/data`를 연결하는 기준 ([상세 계약](daily_update_phase4_analysis_reporting_web_contract_v01.md) 참고) |
| 5단계 | 최종 검증·배포 | 하나의 진입점에서 검증 후 배포하는 최종 묶음. 개요만 정의 |

이 순서는 원천 데이터가 먼저 완성되고, 그 위에 파생·분석·표시 결과가
쌓이는 현재 아키텍처를 따른다. 각 단계는 앞 단계가 완전하게 끝났다고
검증된 경우에만 다음 단계의 입력으로 사용할 수 있다.

## 3. 공통 기준일 계약

### 3.1 유일한 입력

데일리 업데이트는 다음 입력 하나를 받는다.

```text
target_as_of = 사용자가 지정한 포함 기준일
```

`target_as_of`는 호출 계층에서 하위 갱신기와 파생·분석 계층으로 변경 없이
전달한다. 하위 계층은 다음 값을 새 기준일로 만들 수 없다.

- 시스템 날짜 또는 실행 시각
- 저장된 파일의 최신 날짜
- 원천 응답이 돌려준 최신 날짜
- 웹 페이지가 표시하는 최신 날짜

파일의 최신 날짜는 저장 상태를 점검하는 값일 뿐, 사용자가 요청한 기준일을
대체하는 권위가 아니다.

### 3.2 기준일이 거래일이 아닌 경우

`target_as_of` 자체가 주말이나 휴장일이어도 입력은 허용한다. 이때의 의미는
그 날짜까지 실제로 존재해야 하는 거래일을 모두 포함하라는 것이다.
따라서 필요한 거래일 집합은 `target_as_of`를 덮는 검증된 운영 거래일
권위에서 구한다. 현재 운영에서는 `rolling authority`(운영 권위)의
`merged_trading_calendar.json`을 사용한다. 가장 가까운 거래일로 기준일을
바꾸거나, 현재 전체 종목 집합으로 대체하지 않는다.

과거 동결 PIT와 거래일 달력은 과거 기준선으로 보존한다. 운영 권위는 다음
공식 확장 흐름으로 기준일을 전진시킨다.

```text
과거 동결 PIT / 거래일 달력
  → 기존 공식 rolling 확장 절차
  → 검증된 merged PIT / merged 거래일 달력
  → target_as_of 기준 운영 권위
```

`merged_pit_intervals.json`과 `merged_trading_calendar.json`은
`manifest.json`의 권위 경계·해시·스키마 정보와 함께 검증한다. 기준일이 현재
운영 권위의 최신 검증 경계를 넘어서는 경우에는 기존 공식 rolling 확장
구조를 사용한다. Basic Info/PIT/거래일 근거를 확보할 수 없거나 병합 권위
검증에 실패하면 현재 목록이나 임의 규칙으로 우회하지 않고 `BLOCKED`로
처리한다.

예를 들어 토요일을 `target_as_of`로 지정하면 금요일까지의 필요한 거래일이
완성되어야 한다. 토요일이라는 이유로 기준일을 금요일로 다시
기록하지 않는다.

### 3.3 기준일의 전파

한 번의 갱신은 다음처럼 같은 기준일을 공유한다.

```text
target_as_of
  ├─ 공통 원천·수정주가
  ├─ ETF 원천·수정주가
  ├─ 시장 대표지수
  ├─ 종목 정체성·PIT 기준
  ├─ 주봉·월봉
  ├─ 수급·펀더멘털·RS
  ├─ 스캐너·전략·종목 리포트
  └─ 랭킹·공포지수·웹 데이터
```

어느 가지라도 다른 날짜를 사용하면 한 번의 데일리 업데이트가 아니며,
최종 결과는 정상 완료로 판정하지 않는다.

## 4. 증분 갱신과 재실행 안전성

### 4.1 필요한 날짜만 계산한다

갱신 대상은 단순히 `최신 파일 날짜 이후`가 아니다. 기준일 이하의 필요한
거래일 집합과 각 데이터 계층의 완료된 날짜 집합을 비교하여 **빠진 날짜를
정확히 계산**한다.

```text
검증된 운영 거래일 권위의 필요한 거래일 집합(target_as_of 이하)
  - 계층별 완료된 거래일 집합
  = 해당 계층의 갱신 대상
```

따라서 최신 날짜가 같아도 중간 날짜가 비어 있으면 그 중간 공백을 찾아
갱신해야 한다. `max(date)`만 확인해서 완료로 처리하지 않는다.

### 4.2 갱신 예시

| 계층 상태 | `target_as_of` | 처리 |
|---|---|---|
| 일부 필요한 거래일만 확보 | `target_as_of` | 필요한 거래일 집합과 완료 집합의 차이만 갱신 |
| 필요한 거래일 집합 전체 확보 | `target_as_of` | 수집·저장 없이 `NOOP`으로 처리 |
| 필요한 거래일 사이에 공백 존재 | `target_as_of` | 중간 공백을 탐지해 해당 거래일만 갱신 |

공휴일과 주말은 누락 거래일이 아니다. 검증된 운영 거래일 권위에서 필요한
거래일인지 먼저 판정하고, 필요한 거래일만 완료 여부를 확인한다.

### 4.3 기존 이력 보존

증분 갱신은 다음 원칙을 지킨다.

- 이미 유효한 과거 데이터를 매일 다시 내려받지 않는다.
- 매일 전체 이력을 전수 재검색하거나 전체 파일을 다시 만들지 않는다.
- 빠진 날짜 또는 명시적으로 변경 승인을 받은 데이터만 대상으로 삼는다.
- 정상적인 동일 기준일 재실행은 파일·메타데이터·권위 경계를 바꾸지 않는다.
- 같은 입력과 같은 기준일에 대해 결과가 달라지지 않도록 결정적이고
  멱등적으로 처리한다.

기업행위에 따른 과거 수정은 일반 증분 수집과 구분한다. 현재 수정주가
저장소와 원천 저장소의 의미, 검증, 변경 감지 계약을 우회해서 과거 이력을
조용히 덮어쓰지 않는다.

## 5. 1단계: 데일리 업데이트 기반

### 5.1 목표

하나의 `target_as_of`에 대해 핵심 시장데이터 계층이 필요한 거래일까지
완성되고, 각 결과를 `MarketDataRepositoryV2`에서 동일한 거래 세션 의미로 읽을 수
있게 만드는 것이 1단계의 목표다.

### 5.2 포함 범위

1단계의 완료 판정에는 다음 계층이 포함된다.

| 계층 | 기준과 역할 |
|---|---|
| 공통 원천 | KOSPI·KOSDAQ 일반 종목의 KRX 원천 일별 데이터 |
| 공통 수정주가 | 일반 종목의 `AdjustedPriceStore` V02 수정주가 OHLC |
| ETF 원천 | ETF 원천 일별 데이터. 현재 검증된 ETF Repository V2 범위를 임의로 넓히지 않음 |
| ETF 수정주가 | ETF의 수정주가 OHLC. ETF 원천의 거래량·거래대금으로 재구성하지 않음 |
| 시장 대표지수 | 현재 `IndexStore`의 KOSPI·KOSDAQ 대표지수 계층 |
| 종목 집합·PIT | 기준일에 유효한 종목 정체성과 필요한 PIT·운영 거래일 권위 |
| 기업행위 / 수정주가 재검증 | 관리 대상 종목의 기업행위 변경 여부 확인, 영향받은 수정주가를 필요한 경우 재검증·갱신. `DIRTY`/`FAILED` 상태가 남으면 1단계 `PASS` 금지 |
| Repository V2 | 수정주가 OHLC와 원천 부가 데이터를 엄격한 거래 세션 의미로 결합하는 최종 읽기 계층 |

공통·ETF의 원천과 수정주가 의미를 서로 바꾸지 않는다. 수정주가 OHLC는
`ADJUSTED`, 거래량·거래대금·시가총액·상장주식수는 원천 `RAW`라는 현재
Repository V2 계약을 그대로 따른다.

### 5.3 공식 처리 순서

1. `target_as_of`를 입력한다.
2. 각 계층의 현재 완료 상태와 권위 경계를 점검한다.
3. `target_as_of` 이하의 필요한 거래일을 검증된 운영 거래일 권위에서 계산한다.
4. 기준일에 유효한 종목 정체성과 PIT 근거를 확보한다.
5. 각 시장데이터 계층별로 필요한 날짜와 완료 날짜의 차이를 계산한다.
6. 빠진 날짜만 증분 갱신한다.
7. 각 계층이 기준일까지 완전한지 검증한다.
8. `MarketDataRepositoryV2`의 종목·날짜 결합 조회와 거래 세션 의미를 검증한다.
9. 전체 결과를 종합해 상태를 확정한다.

6번과 7번 단계에는 기업행위 확인과 영향받은 수정주가 재검증이 포함된다.
관리 대상 종목에 `DIRTY`/`FAILED` 상태가 남아 있으면 9번 단계에서 전체
결과를 `PASS`로 확정하지 않는다.

이 순서는 별도 우회 경로를 추가하기 위한 것이 아니다. 현재 데이터 아키텍처의
원천 → 저장소 → Repository V2 경계를 유지하면서, 갱신 기준일만 공통으로
전달하기 위한 순서다.

### 5.4 계층별 현재 기준

#### 공통 원천

기존 KRX 원천 저장소와 롤링 백필 경로를 재사용한다. 기준일 이하에서 빠진
필요 거래일만 갱신하며, 저장소의 완료 상태와 실패 상태를 구분한다.
공통 원천이 기준일보다 앞서 있다는 이유만으로 중간 공백을 완료로 간주하지
않는다.

#### 공통 수정주가

현재 `AdjustedPriceStore` V02의 Naver 직접 날짜 범위 수정주가 OHLC 계약과
Repository V2 결합 규칙을 따른다. 공통 종목의 증분 범위를 계산하려면
기준일에 유효한 PIT 공통 분모와 검증된 운영 거래일 권위가 함께 필요하다.

과거 동결 PIT와 거래일 달력을 직접 변경하지 않는다. 기존 공식 rolling
확장 절차인 `build_rolling_pit_extension()`으로 동결 기준 이후의 근거를
확장하고, 검증된 `merged_pit_intervals.json`과
`merged_trading_calendar.json`을 운영 권위로 사용한다. 확장 결과는
`manifest.json`의 권위 경계·해시·스키마와 일치해야 한다.

현재 운영 PIT·거래일 권위가 `target_as_of`를 덮지 못하면 rolling 확장으로
전진을 시도한다. 필요한 Basic Info/PIT/거래일 근거를 확보할 수 없거나
확장 결과가 검증되지 않으면 새 임의 규칙, 현재 종목 목록, 임의 날짜로
대체하지 않고 `BLOCKED`로 처리한다. 이는 일반 종목 수정주가를 원천
데이터보다 앞서거나 뒤처진 상태로 승격하지 않기 위한 필수 전제다.

#### ETF 원천·수정주가

현재 Repository V2에서 검증된 ETF 범위와 원천·수정주가 분리를 유지한다.
ETF 우주를 종목코드 형식, 이름, 임의 허용 목록으로 새로 정의하지 않는다.
ETF 원천의 거래량과 거래대금은 원천 필드를 그대로 보존하며 수정주가 OHLC로
계산하지 않는다. 원천 인증이나 활용 승인이 되지 않으면 성공을 가장하지
않고 `DATA_UNAVAILABLE: RAW_MISSING`으로 안전하게 차단한다.

ETF raw authority의 운영 coverage lower bound는 해당 원천 계약에서 정의한다.
이는 KRX 원천 자체의 전체 역사 제공 가능 여부를 주장하는 값이 아니라, 현재
프로젝트가 검증해 운영에 사용하는 ETF raw authority의 시작점이다. 그 경계
이전의 거래일은 ETF raw 누락이나 완료 게이트 차단 대상으로 계산하지 않는다.
ETF raw historical scope를 경계보다 과거로 확대하는 작업은 별도 승인
범위이며, ETF raw whole-market 계층과 ETF adjusted 계층의 시작 경계는 각
저장소 계약을 따른다.

#### 시장 대표지수

현재 `scripts/refresh_market_index_v01.py`의 증분 구조를 기준으로 한다.
공통 원천의 KOSPI·KOSDAQ 완료 상태를 바탕으로 기준일 이하의 후보 날짜를
계산하고, 이미 존재하는 날짜를 다시 수집하지 않는다. 두 대표지수 코드의
날짜 쌍이 모두 완전해야 하며, 중복·불완전한 날짜 쌍·과거 행 변경은
차단한다. 필요한 날짜가 없으면 저장소를 변경하지 않는 `NOOP`이 될 수 있다.

#### 종목 집합·PIT

종목 정체성은 `(ticker, ISU_CD, market)` 의미를 보존한다. 현재 운영
메타데이터 조회는 `InstrumentMetadataResolver`의 로컬 PIT 기준을 사용하며,
미래 `effective_date`를 사용하지 않고, 공식 분류와 신뢰 조건을 만족하지
못하면 안전하게 차단한다.

과거 백테스트의 생존편향 방지 분모는 현재 운영 메타데이터 목록과 같은
질문으로 취급하지 않는다. 전체 종목 집합과 날짜별 `PIT 공통 분모`를
하나의 정적 목록으로 합치지 않으며, 각 사용 목적에 맞는 권위 산출물을
선택한다.

#### 기업행위 / 수정주가 재검증

현재 구현에서 기업행위 확인은 1단계 완료 판정의 필수 게이트다. 관리 대상
종목에 대해 기준일 이하 관찰 구간의 기업행위 스냅샷을 평가하고, 상태가
`DIRTY` 또는 `FAILED`로 남은 종목의 수정주가를 재검증·재수집한다. 재검증
이후에도 `DIRTY`/`FAILED` 상태가 남은 종목이 있으면 즉시 차단하며, 최종
완료 검증에서도 이 게이트가 `PASS`이고 남은 `DIRTY`/`FAILED` 상태가 없는지
다시 확인한다. 어느 경우든 `DIRTY`/`FAILED` 상태가 남아 있으면 1단계 전체
결과를 `PASS`나 `NOOP`으로 승격하지 않는다.

#### Repository V2 최종 읽기

Repository V2는 읽기 전용 결합 계층이다. 수정주가 가격과 원천 부가 데이터의
거래 세션 집합과 데이터 의미를 확인하고, 날짜 불일치·한쪽만 존재하는
데이터·공유 자리표시자 충돌을 조용히 채우거나 제거하지 않는다. 필요한
거래 세션 의미를 증명할 수 없으면 `DATA_UNAVAILABLE` 또는 정의된 `BLOCKED_*`
상태로 안전하게 차단한다.

### 5.5 1단계 완료 상태

1단계 결과는 다음 네 상태 중 하나다.

| 상태 | 의미 |
|---|---|
| `PASS` | 모든 필수 계층이 기준일까지 완전하고, 기업행위 게이트가 `PASS`이며 `DIRTY`/`FAILED` 상태 종목이 없고, Repository V2 최종 조회도 정상 |
| `NOOP` | 이미 기준일까지 완전하여 수집·저장 변경이 없음. 실패가 아닌 정상 완료 |
| `BLOCKED` | 권위·인증·PIT·원천 데이터·거래 세션 의미 중 하나를 확인할 수 없어 차단 |
| `FAILED` | 계약상 예상하지 못한 오류가 발생함 |

`NOOP`은 변경이 없다는 이유로 `FAILED`로 낮추지 않는다. 반대로 일부 계층만
완료된 경우에는 `PASS`나 `NOOP`으로 승격하지 않는다.

필수 계층 중 하나라도 기준일까지 필요한 거래일을 확보하지 못하면 전체 결과는
`PASS`가 아니다. 해당 계층의 차단 사유를 남기고 전체 데일리 업데이트를
`BLOCKED`로 처리한다.

기업행위 게이트도 동일한 원칙을 따른다. 관리 대상 종목에 `DIRTY`/`FAILED`
상태가 남아 있으면 다른 계층이 모두 완료되었더라도 전체 결과를 `PASS`로
승격하지 않고 `BLOCKED`로 처리한다.

### 5.6 결과 기록 형식

```text
데일리 업데이트 기반
기준일: target_as_of
일반 종목 원천 데이터: <상태>
일반 종목 수정주가: <상태>
ETF 원천 데이터: <상태>
ETF 수정주가: <상태>
시장 대표지수: <상태>
Repository V2: <상태>
최종 결과: PASS / NOOP / BLOCKED / FAILED
```

실제 결과에는 각 계층의 상태, 기준일, 갱신한 날짜 수, 중간 공백 수,
차단 사유가 함께 남아야 한다. 기준일과 상태를 생략한 “업데이트 완료”만으로
정상 완료를 주장하지 않는다.

## 6. 2~5단계의 상위 기준

아래는 전체 업데이트 흐름에 필요한 상위 계약이다. 2단계와 3단계의 세부
산식·저장 형식·실행 구현은 연결된 상세 계약에서 정의한다. 4~5단계의 세부
구현은 이 문서에서 확정하지 않는다.

### 6.1 2단계: 주봉·월봉 파생

주봉·월봉은 독립 원천이 아니라 1단계의 일봉 데이터에서 파생한다. 기준일
이전의 완성된 거래봉만 `COMPLETE`로 취급하며, 기준일이 아직 끝나지 않은
주간·월간 구간은 `PROVISIONAL`로 구분할 수 있다. 기존 완성 봉을 다시
열린 상태로 바꾸거나, 주봉·월봉을 독립 원천처럼 수집하지 않는다. 상세
파생 규칙과 상태 저장 형식은 이 문서에서 확정하지 않는다.

### 6.2 3단계: 분석 입력 갱신

수급, 펀더멘털 변경, 시장·업종 RS, 섹터 구성 등 추가 입력은 같은
`target_as_of`를 상속한다. 각 원천은 자신의 누락 거래일·공시일·효력일
규칙을 가질 수 있지만, 기준일을 실행 시각으로 바꾸거나 현재 목록을 과거에
전파하지 않는다. 5개 최상위 입력의 증분 규칙·의존성·상태 합성·공식
진입점은 [분석 입력 갱신 기준
V01](daily_update_phase3_analysis_inputs_contract_v01.md)에서 정의한다.

### 6.3 4단계: 분석·리포트·웹 반영

스캐너, 공식 전략, 시장·업종 RS, 종목 리포트, 랭킹, 공포지수,
`web/data`는 1~3단계가 확정한 동일한 기준일을 사용한다. 일부 입력만 최신이고
일부 입력은 이전 기준일이면 결과를 최신으로 표시하지 않는다. 분석 결과와
웹 산출물은 검증을 통과한 경우에만 배포 대상으로 삼는다. 기존 경로의 재사용,
필수·선택 투영 구분, 상태 합성과 구현 전제는 [분석·리포트·웹 반영 기준
V01](daily_update_phase4_analysis_reporting_web_contract_v01.md)에서 정의한다.

### 6.4 5단계: 최종 검증·배포

최종 실행은 하나의 진입점에서 하나의 `target_as_of`를 전달하고, 단계별
상태와 기준일을 요약한 뒤 검증을 통과한 결과만 배포한다. 스케줄러나 실행
주기는 이 문서에서 고정하지 않는다. 자동 실행 여부와 관계없이 수동 실행과
동일한 기준일·검증·차단 규칙을 적용한다.

## 7. 모든 단계에 상속되는 규칙

- 기준일 입력은 하나이며 `target_as_of`를 그대로 전달한다.
- 필요한 날짜 집합과 계층별 완료 집합의 차이로 누락을 찾는다.
- 최신 날짜만 비교하지 않고 중간 공백을 탐지한다.
- 유효한 과거 이력을 불필요하게 다시 수집하거나 덮어쓰지 않는다.
- 같은 입력과 같은 기준일의 정상 재실행은 멱등적이어야 한다.
- 한 계층만 성공한 부분 성공을 전체 성공으로 보고하지 않는다.
- 권위·PIT·인증·거래 세션 의미를 증명할 수 없으면 우회하지 않고 차단한다.
- 검증이 끝나기 전에는 다음 단계나 배포를 완료 상태로 승격하지 않는다.

공통 날짜·증분·완료 상태 규칙을 바꾸려면 먼저 이 문서를 검토하고
업데이트한다. 그 후 구현과 개별 데이터 계약을 같은 기준에 맞춘다.

## 8. 구현과 문서의 권위 관계

구현은 이 문서와 연결된 현재 아키텍처 문서를 따라야 한다. 구현이 문서와
다르면 먼저 그 차이가 단순한 미구현인지, 운영 기준 변경인지 확인한다.
운영 기준을 바꾸는 경우에는 구현 차이를 먼저 확인하고 문서를 뒤늦게 고치는
대신, 문서를 먼저 검토·갱신하고 승인된 기준에 맞춰 구현을 정렬한다.

특히 다음 우회는 허용하지 않는다.

- 하위 함수가 시스템 날짜를 읽어 `target_as_of`를 덮어쓰기
- 최신 파일 날짜만 보고 기준일까지 완료되었다고 판단하기
- 중간 공백을 무시하고 `max(date)`만으로 완료 판정하기
- PIT 경계가 부족한데 현재 종목 목록이나 임의 날짜로 대체하기
- 원천과 수정주가의 의미를 섞거나 Repository V2에서 값을 채우기
- 일부 계층 성공을 전체 `PASS`로 승격하기
