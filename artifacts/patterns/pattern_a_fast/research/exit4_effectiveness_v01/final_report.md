# A FAST Core V2 — Exit4 Effectiveness & PROGRESSED Departure Comparison V01

## Verdict

- **Exit4는 조기 청산이 아니라 대부분 선행 청산이다.** Exit4 이후 실제로 PROGRESSED를 이탈한 1,231건(결과가 완결된 거래)에서 이탈까지 기다렸다면 중앙 -19.8pp, 평균 -12.5pp 나빴다. Exit4 쪽이 나은 거래가 766건, 나쁜 거래가 254건이고, 모든 단순·현실적 윈도우와 거의 모든 연도에서 반복된다.
- **Exit4가 runner를 끊은 부분도 있다.** cutoff까지 이탈이 없던 240건에서는 계속 보유했다면 평균 +83pp, 중앙 +12.6pp 나았다.
  - 다만 이 240건 중 203건은 Exit4가 2025~2026년에 발생했다. 윈도우 끝(2026-08-31)에서 잘린 미완결 표본이고 반사실은 cutoff 종가 평가값이다.
  - 평균은 몇 건의 극단 winner(최대 +3,016%)가 좌우한다.
- **Exit4 제거 시(1,471건 전체):** deep loss가 늘고(-30% 이하 7 → 78건) +50% winner는 줄어든다(710 → 530). +100% winner는 같다(287 → 288).
- **다음 단계:** Exit4 유지. 제거 후보 연구는 근거가 없다. 수정 후보 연구(runner 보존)는 절단된 표본에만 근거가 있어 현재로서는 근거가 부족하다.

새 백테스트, 전략·청산 규칙 변경, threshold sweep, 네트워크 호출은 모두 0건이다. 반사실은 거래 단위이며 포트폴리오 재배치는 계산하지 않았다.

## 1. Exit4 정의 (production 코드 기준)

인증 러너가 호출하는 `src/trend_scanner/validation/pattern_a_fast_core_v02_reentry.py`의 `simulate_ticker_core_v02_reentry`를 기준으로 삼았다.

**NORMAL 경로(`EARLY_TREND → PROGRESSED` 직접 handoff가 있는 거래)**
- 첫 직접 handoff 라벨에서 HWM을 그 라벨의 Pattern A 점수로 초기화한다.
- 이후 PROGRESSED 월 라벨마다 `HWM = max(HWM, 점수)`로 갱신하고, `HWM - 점수 ≥ 15.0`이면 Exit4다.
- WEAK·BASE·TRANSITION·EARLY_TREND 라벨이 나오면 Exit3다. UNAVAILABLE은 무시한다.

**coverage 경로(SKIPPED / WITHOUT_DIRECT)**
- 첫 PROGRESSED 라벨의 점수로 HWM을 초기화하고, PROGRESSED 라벨에서만 Exit4를 본다.
- PROGRESSED가 아닌 라벨(UNAVAILABLE 포함)이 나오면 감시를 끝내고 청산 없이 미청산으로 남는다.

**우선순위와 체결**
- -15% Loss Guard는 첫 PROGRESSED 관측 이전에만 작동하고, 발동하면 E2(Exit3·Exit4)보다 우선한다.
- 한 월 라벨에서 Exit3와 Exit4는 동시에 성립할 수 없다. Exit4는 PROGRESSED 라벨에서만 성립한다.
- 체결은 신호 라벨보다 뒤의 첫 거래일 시가다(실행 지원일 포함). Exit4 시점 stage는 정의상 항상 PROGRESSED다.

**문서와 실제 동작의 차이**
- V2 README는 체결을 "익월 첫 로컬 거래일 시가"로 적었지만, 코드는 "신호 라벨 다음 거래일 시가"다. 월말 라벨이면 두 표현은 같다.
- 실서비스 리포트(`a_fast_core_report.py`)는 HWM을 표시만 하고 청산 판정은 하지 않는다.

## 2. 검증

| 항목 | 결과 |
|---|---|
| E2 청산 유형·신호일 재현(Loss Guard·정산 제외 전 거래) | 단순 P1·P2-1·P3-1·P3-2, 현실적 6개 패널 100%, 단순 P2-2 99.9%(981 / 982, 이전 데이터 authority) |
| Exit4 신호 재현 | 모든 패널 100% |
| Exit4 체결가(다음 거래일 시가) | 모든 패널 100% |
| stage 캐시 누수 점검, 원장 lifecycle 재현 | 상위 분석 게이트 통과 |
| 거래 identity 중복 | 0 |

**반사실 `CF_NO_EXIT4_UNTIL_PROGRESSED_DEPARTURE`**
- Exit4 신호를 무시하고 그 이후 첫 유효 non-PROGRESSED 라벨(UNAVAILABLE 제외)의 다음 거래일 시가에 청산한다. 가격 규칙은 이전 분석에서 Exit3 실체결 763건과 100% 일치했다.
- 이탈이 윈도우 cutoff까지 없으면 cutoff 종가로 평가한다.
- Loss Guard는 첫 PROGRESSED 이후 비활성이라 다른 강제 청산은 없다.
- 이 반사실은 정의상 실제 청산 이후의 가격·stage를 쓴다. 다만 윈도우 cutoff를 넘지 않는다.

**분류 기준(결과 확인 전에 고정):** 반사실 - 실제(pp)로 나눈다.
- ≤ -10pp는 `EXIT4_CLEARLY_HELPFUL`이다.
- |차이| < 10pp는 `EXIT4_ROUGHLY_REDUNDANT`다.
- ≥ +10pp는 `EXIT4_POTENTIALLY_HARMFUL`이다.
- 계산 불가는 `INSUFFICIENT_EVIDENCE`다(해당 0건).

## 8. 질문별 답

1. **Exit4는 deep loss를 의미 있게 줄였는가?** 줄였다. 없었다면 -30% 이하 7 → 78건, -50% 이하 3 → 10건이다.
2. **+50 / +100 winner를 얼마나 훼손했는가?**
   - 반사실 대비 +50% winner는 오히려 180건 더 지켰다(잃음 293, 얻음 113).
   - +100% 이상은 147건을 잃고 148건을 얻어 순효과가 0이다.
   - Exit4 이후 고점이 +100%를 넘긴 거래는 472건이지만, 대부분 이탈 전에 되돌려졌다.
3. **Exit4 이후 실제 PROGRESSED 이탈까지 기다렸다면 더 좋았는가?**
   - 결과가 완결된 A 그룹에서는 나빴다(중앙 -19.8pp).
   - 이탈이 없던 B 그룹은 좋았지만(중앙 +12.6pp) 대부분 2025~2026년 절단 표본이다.
4. **Exit4와 Exit3는 역할이 중복되는가?** 중복되지 않는다. Exit4가 중앙 225거래일 먼저, 중앙 20pp 높은 가격에 청산한다.
5. **Exit4가 반드시 필요한 거래 유형이 있는가?** coverage 경로다(Exit3 부재로 Exit4가 유일한 청산). NORMAL 경로에서도 PROGRESSED 안에서 점수가 꺾이는 추세 약화 구간에서는 Exit4가 먼저 이익을 확정한다.
6. **Exit4 제거 후 PROGRESSED 이탈 청산 하나로 단순화할 근거가 있는가?** 없다.
7. **다음 단계:** Exit4 유지.
   - 수정 후보(runner 보존) 연구는 B 그룹이 근거지만, 절단되고 극단값에 좌우되는 표본이라 현재로서는 근거가 부족하다.
   - 윈도우 cutoff 이후 데이터가 쌓여 B 그룹이 완결되면 다시 볼 가치가 있다.

## 해석 주의

- **반사실의 성격:** 청산 규칙 하나만 바꾼 거래 단위 가정이다. 포트폴리오 자본 재배치와 이후 재진입 변화는 반영하지 않았다.
- **B 그룹:** 윈도우 cutoff 종가 평가다. 미래 결과가 아니다.
- **극단값:** 평균 차이는 극단 winner에 크게 흔들린다. 중앙·건수·top N 제외 값을 함께 봐야 한다.
- **인과:** 상관을 인과로 단정하지 않는다.
